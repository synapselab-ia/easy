## Authorization / RLS contract

RLS is enabled on all five public tables.

The initial single-operator authorization model is:

1. identity comes from Supabase Auth (`auth.uid()`);
2. only an active UUID in `public.easy_operators` is an Easy operator;
3. an authenticated user outside that allow-list sees no business rows;
4. `anon` has no table access;
5. `easy_operators` is client read-only and exposes only the current user's own allow-list row through RLS;
6. category/item/reseller CRUD is permitted only to authenticated approved operators;
7. `transactions` grants authenticated users SELECT only — browser direct INSERT/UPDATE/DELETE is intentionally unavailable.

Synthetic authorization proof used non-real UUIDs only:

- approved synthetic Auth UUID returned `is_easy_operator = true`;
- non-approved synthetic Auth UUID returned `false` and saw 0 categories / 0 operator rows;
- `anon` SELECT on `categories` failed with PostgreSQL `42501`;
- direct authenticated INSERT into `transactions` failed with PostgreSQL `42501`;
- non-approved authenticated RPC execution failed with PostgreSQL `42501`.

No real operator email/account was provisioned in P10-S3-I1. Real operator onboarding remains part of a later migration/cutover gate and must not be simulated by manually inserting an `auth.users` row.

## Financial write boundary

Public Data API financial writes are exposed through three RPC contracts:

- `public.create_transaction`;
- `public.reverse_transaction`;
- `public.correct_transaction`.

The public RPCs are `SECURITY INVOKER` wrappers. Privileged implementations live in the non-exposed `private` schema, use fixed empty `search_path`, and explicitly require the Auth UUID to be an active Easy operator before mutating data.

This split was added after the initial Supabase Security Advisor correctly warned that authenticated users could call public `SECURITY DEFINER` functions. After hardening, Security Advisor returned **0 lints**.

`transactions` cannot be mutated directly by the browser, preventing a client from forging reversal/correction linkage fields outside the server/database transaction boundary.
